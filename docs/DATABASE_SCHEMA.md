# Database Schema Specification

This document details the PostgreSQL relational schema and Redis caching structures for the StreetFoodAI platform.

---

## 1. Relational Schema (PostgreSQL)

We will use **PostgreSQL** for structural consistency, transactional billing, and analytics. All primary keys are UUIDs generated by the application layer.

    USERS ||--o{ SEARCH_LOGS : "performs"

    USERS {
        uuid id PK
        varchar phone UNIQUE

    }

    VENDOR_PROFILES {
        uuid id PK "FK to users.id"

        double_precision last_longitude

        uuid id PK

        varchar description

        timestamptz created_at
    }

    SEARCH_LOGS {
        uuid id PK

        double_precision longitude
        uuid user_id FK "nullable"
        timestamptz created_at
    }

## 2. Table Definitions

### `users`
Stores user authentication details and system roles.
- `id` (UUID, Primary Key): Unique identifier.
- `phone` (VARCHAR(15), Unique, Indexed): User phone number (acts as username).
- `password_hash` (VARCHAR(255)): Secure password hash.
- `role` (VARCHAR(10)): System role (`vendor` or `customer`).
- `created_at` (TIMESTAMPTZ, Default NOW()): Row creation timestamp.
- `updated_at` (TIMESTAMPTZ, Default NOW()): Row update timestamp.

### `vendor_profiles`
Additional profile metadata for users who are vendors.
- `id` (UUID, Primary Key, Foreign Key to `users.id` ON DELETE CASCADE).
- `business_name` (VARCHAR(100)): Display name of the vendor.
- `description` (TEXT, Nullable): Short description of offerings.
- `is_active` (BOOLEAN, Default FALSE): True if vendor is currently online.
- `status` (VARCHAR(20), Default 'closed'): Operation status (`open`, `closed`, `moving`).
- `last_latitude` (DOUBLE PRECISION, Nullable): Last known lat coordinate.
- `last_longitude` (DOUBLE PRECISION, Nullable): Last known lon coordinate.
- `last_location_updated_at` (TIMESTAMPTZ, Nullable): Timestamp of last GPS ping.
- `rating` (NUMERIC(3, 2), Default 5.00): Customer feedback rating.

### `products`
The vendor menu.
- `id` (UUID, Primary Key).
- `vendor_profile_id` (UUID, Foreign Key to `vendor_profiles.id` ON DELETE CASCADE, Indexed).
- `name` (VARCHAR(100)): Food item name.
- `description` (TEXT, Nullable).
- `price` (NUMERIC(10, 2)): Item unit price.
- `category` (VARCHAR(50), Default 'snacks'): Category for menu filtering.
- `is_available` (BOOLEAN, Default TRUE): Whether item is currently in stock.
- `created_at` (TIMESTAMPTZ, Default NOW()).

### `transactions`
Sales tickets recorded by the vendor POS.
- `id` (UUID, Primary Key).
- `vendor_profile_id` (UUID, Foreign Key to `vendor_profiles.id` ON DELETE SET NULL, Indexed).
- `total_amount` (NUMERIC(10, 2)): Sum of transaction items.
- `payment_method` (VARCHAR(20), Default 'cash'): Payment method used.
- `created_at` (TIMESTAMPTZ, Default NOW(), Indexed): Essential for historical demand aggregating.

### `transaction_items`
Line items for each transaction.
- `id` (UUID, Primary Key).
- `transaction_id` (UUID, Foreign Key to `transactions.id` ON DELETE CASCADE, Indexed).
- `product_id` (UUID, Foreign Key to `products.id` ON DELETE RESTRICT, Indexed).
- `quantity` (INTEGER): Quantities sold.
- `unit_price` (NUMERIC(10, 2)): Unit price at time of sale (preserves history if product price changes).

### `expenses`
Operational expenses logged by the vendor.
- `id` (UUID, Primary Key).
- `vendor_profile_id` (UUID, Foreign Key to `vendor_profiles.id` ON DELETE CASCADE, Indexed).
- `amount` (NUMERIC(10, 2)): Total cost.
- `description` (VARCHAR(255)): Item details.
- `category` (VARCHAR(50)): Category (`raw_materials`, `gas`, `rent`, `other`).
- `created_at` (TIMESTAMPTZ, Default NOW(), Indexed).

### `search_logs`
Geospatial customer search queries. This table logs raw demand data.
- `id` (UUID, Primary Key).
- `query` (VARCHAR(100), Indexed): Search keyword (e.g. 'momos').
- `latitude` (DOUBLE PRECISION): GPS latitude.
- `longitude` (DOUBLE PRECISION): GPS longitude.
- `user_id` (UUID, Nullable, Foreign Key to `users.id` ON DELETE SET NULL).
- `created_at` (TIMESTAMPTZ, Default NOW(), Indexed): Aggregated hourly for heatmaps.

## 3. Geospatial Indexing & Caching (Redis)

Because movable vendors will post their locations frequently (every 30s), writing to PostgreSQL on every ping will cause database bloat. Instead, we use a hybrid Redis approach:

### Active Vendor Geospatial Set
Active vendor locations are written to a Redis Geospatial Sorted Set.
- **Key**: `vendor:locations`
- **Data Structure**: Geospatial Index (built-in Sorted Set)
- **Commands**:
  - Update: `GEOADD vendor:locations <longitude> <latitude> <vendor_profile_id>`
  - Delete (on logout): `ZREM vendor:locations <vendor_profile_id>`
  - Query (Find vendors within 1.5km of customer): `GEORADIUS vendor:locations <customer_lon> <customer_lat> 1.5 km WITHCOORD`

### Vendor Status Cache
Vendor profile status updates are cached in Redis to avoid hitting Postgres for simple list renders.
- **Key**: `vendor:status:<vendor_profile_id>`
- **Data Structure**: Hash
- **Fields**:
  - `status`: `open` | `closed` | `moving`
  - `business_name`: String
  - `rating`: Decimal
  - `updated_at`: ISO Timestamp

## 4. Key Performance Indexes

To ensure fast queries during demand calculations, we will add the following indexes:
1. `idx_transactions_vendor_created`: `transactions(vendor_profile_id, created_at DESC)` (for generating vendor dashboards and models).
2. `idx_search_logs_query_created`: `search_logs(query, created_at DESC)` (for finding recent search activity).
3. `idx_search_logs_geo`: B-Tree indexes on `latitude` and `longitude` (allows simple bounding box queries without PostGIS overhead).
